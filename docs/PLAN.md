## 2. Reusable components / page anatomy

- **Header:** logo/site name, nav (Home / All Tools / Categories / Popular), search, theme toggle. (Per-tool screens showed a *different*, inconsistent nav — treated as AI-generation drift; Home's nav was adopted as canonical.)
- **Hero (Home only):** headline + subhead, search bar, popular-tool shortcuts.
- **Tool card:** icon + title + description, used in category grids.
- **Tool page template** (all 20 tools share this shape): breadcrumb-ish header (title + description) → Parameters/input panel → Output panel (result cards, or mono-font output box with copy/refresh icon buttons) → optional visualization (charts, strength meter) → educational content/FAQ → footer.
- **Footer:** copyright, Tools/About/Contact, Privacy/Terms/Disclaimer.

## 3. Design tokens

Source: Stitch's generated `design.md` (YAML front-matter = literal token values, prose = usage rules). Where the prose and the YAML disagreed on a hex value, **the YAML was treated as ground truth** since it's the structured/precise artifact; prose was used for usage rules and for the gaps YAML didn't cover (dark mode, input fill).

**Fonts:** Geist (headings/labels/UI) · Inter (body) · JetBrains Mono (code/output)

**Type scale:** display 48/700 → headline-lg 32/600 (24px mobile) → headline-md 20/600 → body-lg 16 → body-md 14 → label-sm 12/500 → mono 13

**Color (light):** bg `#FCF9F8` · card `#FFFFFF` · primary `#0070F3` (hover `#0058C3`) · secondary `#4648D4` · muted `#F0EDED` · border `#C1C6D7` · error `#BA1A1A` · input fill `#FAFAFA` (prose-only value, no YAML equivalent)

**Color (dark):** no formal YAML token set was provided — bg `#0A0A0A` / elevated `#1A1A1A` came from prose, the rest (borders, muted, hover states) is our extrapolation. **Needs a real QA pass against the actual dark screenshots in Phase 5.**

**Spacing:** 4px base unit — matches Tailwind's default scale exactly, no override needed. Gutter 24px, mobile margin 16px, desktop margin 40px, container max 1200px.

**Radius:** 8px (buttons/inputs) · 24px (cards/containers) · full (pills/tags)

**Elevation:** 1px low-contrast borders instead of shadows for cards; dropdowns/modals get a subtle 10%-opacity shadow.

## 4. Stack decisions

- **Next.js 16 (App Router) + TypeScript + React 19** — scaffolded via `create-next-app`. Note: Next 16 ships breaking changes vs. older docs knowledge (component-level static/dynamic rendering via Cache Components, generated `LayoutProps<'/'>` types). Bundled docs in `node_modules/next/dist/docs/` are the reference until this is internalized.
- **Tailwind CSS v4** (create-next-app's current default) — config lives in CSS (`@theme` in `globals.css`), no `tailwind.config.ts`.
- **next-themes** for the light/dark toggle (class-based, SSR-safe, no flash-of-wrong-theme).
- **lucide-react** for icons instead of literal Material Symbols — equivalent minimalist line-icon look, React components instead of an icon font.
- **shadcn/ui convention adopted for CSS variable naming** (`background`/`foreground`/`primary`/`card`/`border`/`ring`/`radius`, mapped from Stitch's tokens) even though the shadcn CLI/Radix components aren't installed yet — costs nothing now, means Phase 2 (lots of form controls across 20 tools) can adopt shadcn/ui directly against tokens that already match the Stitch palette.
- **npm** as package manager (matches what was available; create-next-app already used it).

- ✅ **Phase 4 — URL Shortener** (2026-08-09): the one tool needing a real backend, built from the user's pasted literal Stitch HTML, same process as every other rebuilt page.
  - **Storage: Upstash Redis** (REST-based, serverless-friendly — user's choice over SQLite-file or in-memory, see chat). `lib/redis.ts` (singleton client, throws a clear setup error on first use if env vars are missing rather than an opaque fetch failure), `lib/url-shortener.ts` (code generation + `SET ... NX` atomic collision-checked write + lookup), `lib/rate-limit.ts` (`@upstash/ratelimit`, 10 creations/min/IP — the only publicly-writable endpoint on this site).
  - Routes: `POST /api/shorten` (validates http(s)-only, rejects a self-referential `/s/*` link to avoid a redirect loop, rate-limited, returns `{ code, shortUrl }`) and `GET /s/[code]` (real 301 redirect via `RouteContext<'/s/[code]'>`, matching the tool's own "Is it safe?" copy about standard HTTP 301s; unknown codes redirect back to the tool page with `?notfound=1` rather than a bare 404).
  - `/s/<code>` chosen over a root-level `/<code>` — this project doesn't own a short branded domain like the mockup's fictional `dtls.co`, and a root-level catch-all would risk colliding with real routes as the site grows.
  - **"Recent History" is per-browser localStorage**, not a server-side per-user list — there's no accounts/auth anywhere on this site, so a shared server list would show everyone else's links. Read via `useSyncExternalStore` (React's sanctioned way to read an external mutable store) rather than a mount `useEffect`, avoiding the same `react-hooks/set-state-in-effect` lint footgun noted for UuidGeneratorTool/RandomNumberGeneratorTool. The redirect itself works for anyone with the link regardless of which browser created it — only the convenience history list is local.
  - Rejected reproducing the mockup's placeholder TopNavBar (Finance/Unit Converter/Health/Developer nav + "Sign In" button) — same per-tool-screen AI-generation drift already flagged and rejected project-wide for every other tool (see #2); real site Header/Footer used instead, no auth system exists anywhere on this site.
  - QR Code button is real (via the already-installed `qrcode` package, reusing QrCodeGeneratorTool's approach), not a dead mockup button.
  - Verified end-to-end with live Upstash credentials, not just build-passing: `curl`'d a real create → real 301 redirect to the original URL; confirmed unknown-code graceful fallback; confirmed `javascript:`/`data:`/`ftp:` URLs and self-referential `/s/` links are all rejected; confirmed the rate limiter actually returns 429 under a burst. A standalone script re-ran the real validation/code-generation functions (protocol allowlist, loop guard, 100k-code alphabet/collision sanity check). Playwright end-to-end through the real UI (not mocked) — fill → Shorten → live result → Copy → QR reveal → History row populated — in light, dark, and mobile.
  - New required setup for anyone running this repo: `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` in `.env.local` (placeholders added, real values needed) — documented in README.md. Every other page on the site is unaffected if these are unset; only this tool's "Shorten" action fails, with a clear error rather than a crash.
  - **Follow-up: scoped ACL user + rate-limiter rewrite** (2026-08-09). User created a dedicated `dailytools-url-shortener` Upstash ACL user (rather than using the database's full-access default token) and hit a real platform limitation while scoping it: Upstash's ACL editor rejected `+evalsha` (individual command), `+@scripting` (category), `+pexpire` (individual command — plain, non-scripting), and `+@write` (a totally standard category) in turn, with no discoverable pattern from outside their system — `+get`/`+set`/`+incrby`/`+@read` all went through fine. This isn't a syntax issue; it's an undocumented restriction in Upstash's ACL support (possibly Free Tier-specific, unconfirmed).
    - **Real consequence, not just a config hiccup**: `@upstash/ratelimit` (the original rate-limiter dependency) runs every algorithm it offers — sliding window, fixed window, token bucket — as a Lua script via `EVAL`/`EVALSHA` for atomicity. Since Upstash's ACL can't grant scripting to a restricted user at all, that package could never work under any scoped credential, full stop — no amount of ACL syntax fiddling would fix it.
    - **Fix: replaced `@upstash/ratelimit` entirely** with a ~20-line hand-rolled fixed-window limiter (`lib/rate-limit.ts`) using only `INCRBY` + `PEXPIRE` — both already-working ACL grants. Uninstalled the now-unused package. Tradeoff accepted and documented in the code: fixed-window (not sliding-window) allows up to ~2x the limit right at a window boundary; fine for "cheap insurance against a spam script," not fine if this ever needed to be a hard guarantee.
    - **Final working ACL rule**, after `+@write` also failed: gave up on precise per-command grants and scoped by key pattern only — `ACL SETUSER dailytools-url-shortener on ~url-shortener:* +@all`. Broader than the 4 literal commands the app uses, but the security boundary that actually matters is intact: this credential cannot touch any key outside `url-shortener:*`, vs. the default token which can touch the entire database.
    - REST token for a custom ACL user isn't shown anywhere in Upstash's normal connection-details UI (which only ever shows the `default` user's credentials) — has to be generated explicitly via `ACL RESTTOKEN <username> <password>` in the console's CLI tab, and the user needs a password set first (Upstash auto-generates and one-time-reveals it on user creation; `>password` cannot be typed manually into the ACL rule).
    - Re-verified end-to-end against the actual restricted credential (not the default token) after the swap: real create, real 301 redirect to the correct destination, and the rate limiter firing at exactly request 10 of 12 in a burst test.
  - **Roundup pass** (2026-08-09), prompted by "is it safe without a real DDoS defense?" — closed the gaps identified in that discussion rather than leaving them as known-but-unaddressed:
    - `checkRedirectRateLimit`: `/s/[code]` had zero rate limiting before this — only the create endpoint did. Added a separate 100/min/IP limiter (higher than create's 10/min, since following a shared link is normal high-frequency behavior, not abuse) under its own key prefix so it doesn't share budget with creation.
    - `checkGlobalDailyLimit`: a site-wide (not per-IP) circuit breaker, 2,000 link creations/UTC-day — the real backstop for a *distributed* abuser using many IPs, which per-IP limiting alone can't catch by design. 2,000/day is a starting guess, not a measured number.
    - `rate-limit.ts` refactored around one shared `fixedWindowLimit(key, windowMs, maxRequests)` helper instead of three copy-pasted implementations.
    - `clientIp` extracted to `lib/client-ip.ts`, shared between both route handlers instead of duplicated.
    - `/s/[code]`'s `resolveShortLink()` call is now wrapped in try/catch — previously a Redis outage/quota error here would throw an unhandled exception (Next's default error page) instead of failing gracefully back to the tool page.
    - Added `RedirectNotice` (a small `useSearchParams()`-reading component, wrapped in `<Suspense>` per Next's documented pattern so the rest of the page stays statically prerenderable) so landing on `/tools/url-shortener?notfound=1` or `?error=1` after a dead link actually explains why, instead of silently dumping the visitor on the page with no context.
    - **Explicitly not fixed, and shouldn't be by app code**: real volumetric DDoS (raw bandwidth flooding) is an infrastructure-layer concern — the actual defense is the hosting/CDN edge (Vercel's built-in DDoS protection, or Cloudflare in front of wherever this deploys), not application-level rate limiting. `x-forwarded-for` spoofing is also a known residual gap: per-IP limiting is only as trustworthy as the proxy in front of the app being the one setting that header.
    - Verified: `npm run lint`/`npm run build` clean; the redirect limiter was verified with 120 *concurrent* requests (76 succeeded, 44 correctly rejected) after an initial sequential-curl test gave a false negative (curl's per-request overhead let 105 sequential requests straddle a minute boundary, splitting across two windows) — a reminder that fixed-window rate limits need a concurrent/burst test, not a slow sequential one, to actually exercise the cap.
